1. SPECとの差分

ID 区分 SPECの記述 この設計での扱い 理由
D01 具体化 技術構成は未確定 Node.js 24 + TypeScript、Fastify、React + Vite、Node内蔵SQLite（node:sqlite）、Vitest 6章
D02 具体化 予約の一意制約・時間重複検査をDBトランザクション内で BEGIN IMMEDIATEの直列化に加え、DBトリガーで予約・保留の時間重複を拒否する二重防御 4章。トリガーは2026-11-03にNode v24.22.1で動作を確認
D03 具体化 三者の最小セッション設計 役割ごとの招待リンク（推測不能なトークン）→ 役割と案件範囲に限定したHttpOnlyクッキー。CSRFトークンとOrigin検査 5章
D04 追加 Bの支払い承認が来ない場合の扱いは未記載 実行開始後にBがPayPal画面を閉じた場合は、時間だけで判断せず注文を照会し、未承認と確認できたときだけ凍結を解く 7.4節。SPECの「結果不明の枠を期限切れで解放しない」と整合
D05 追加 予約確定とAへの返金の結び付け方は未記載 予約更新と同じDBトランザクションで、A返金の債務と最初の試行（送信前）を作る（送信待ちキュー方式） 予約確定後に返金が開始されない状態を作らないため
D06 追加 Webhookを業務状態へ反映 Webhookは照会のきっかけにだけ使い、状態はREST照会の結果で更新する 順不同・重複・古い通知で状態が後退しないため
D07 追加 PayPal応答の形式は未記載 与信・売上確定・返金・取消には常にPrefer: return=representationを付ける 既定は最小応答で、与信IDなどが返らない（公式参照、2026-11-03）
D08 具体化 承認は同じ版とハッシュに紐付け 承認順を「店主 → A → B（条件承認と支払い開始を同時）」に固定 Bを先に待たせず、Aが断った時点でBに課金が発生しないため
D09 追加 補償額の確定時点は未記載 補償額は、Aが移動条件を登録した時点の店の規定額を、条件の版と一緒に固定する 待つほど増えない（SPEC 9）を構造で保証するため
D10 追加 公開デモの利用者の分離は未記載 利用者ごとに独立したデモ環境（ワールド）を作り、データ・招待リンク・PayPalの紐付けをワールド単位で分ける 審査員同士の操作が混ざらないため
D11 保留 公開先 ローカル起動を必須の再現手段とする。公開デモの第一候補はCompute Engine＋永続ディスク（Codex第1レビューで推奨） 11章。公開は本人確認後
D12 追加 支払いの試行と案件版の紐付けは未記載 Bの支払いは案件版ごとの「支払い試行」として管理し、期限切れの試行は終了させて、以後の与信を拒否する。再開は新しい案件と再承認で行う 6.3、DR1-01
D13 追加 外部操作は案件ごとに1行 「お金の債務（論理操作）」と「外部への試行」を分ける。確定失敗後だけ新しい試行（新しい再送防止ID）を作れる 7.1、DR1-02
D14 追加 貸出（lease）の扱いは未記載 貸出の所有者と世代番号を保存し、結果の書き込みは世代と状態を条件にした更新だけで行う。状態は後退させない 7.2、DR1-03
D15 変更 Webhookのevent_idに一意制約 受信した配信と、検証済みイベントを別のテーブルにする。一意制約は検証済みイベントだけに置く 7.4、DR1-04
D16 変更 V8は公開工程 V8を必須の接続検証にし、公開デモの採否とは独立して、本人確認後の限定的なHTTPS受信経路で行う 12章、DR1-05

構成は単一プロセスとする。HTTPサーバー、外部呼び出しの実行器、回復処理が同じプロセスで動き、DBファイルは1つ。審査員がローカルで起動する場合も、npm install → npm run devで完結させる。単一プロセスでも、外部通信を待つ間に複数の処理が並行して進むため、二重実行の防止はプロセス内のロックではなくDBの条件付き更新で行う（7.2）。

時刻は、すべてサーバーのClockインターフェース経由で取得する。テストでは時刻を固定・前進させられるようにし、境界試験（AC05）に使う。

3. データモデルと不変条件

金額は通貨の最小単位の整数（USDならセント）。時刻はUTCのエポックミリ秒で保存し、店のタイムゾーンを別に持つ。時間区間は開始を含み終了を含まない（start < other.end AND other.start < endで重複と判定）。

4. 予約枠の競合防止

  1. 直列化：予約・保留・案件状態を変える処理は、すべてBEGIN IMMEDIATEの短いトランザクションで行う。SQLiteは書き込みを1本に直列化するため、「確認してから書く」間に別の書き込みが割り込まない。外部APIの呼び出し中はトランザクションを開かない。
  2. DBトリガー（二重防御）：bookingsの挿入と、時刻・担当者・状態を変える更新の前に、同じ担当者の確定予約、および有効な保留（ACTIVE / FROZEN）と時間が重なればSLOT_CONFLICTで中止する（更新時は自分自身の行を除く）。slot_holdsの挿入と、時刻・担当者・状態を変える更新にも同じトリガーを置く。アプリのコードに誤りがあっても、DBが重複を拒否する。E7の途中でどのSQLが失敗しても、E7全体をロールバックすることをテストで確認する。
  3. 保留の期限：トリガーは時刻に依存させない。期限切れの判定はアプリの時計で行い、同じトランザクションの先頭で、期限を過ぎたACTIVEの保留をRELEASEDに更新してから検査する。FROZEN（実行開始後）の保留は期限で解放しない（SPEC 6）。
  4. 振替の確定順序：1つのトランザクション内で「移動先の保留をCONVERTEDにする → Aの予約を移動先へ更新する → 元枠にBの予約を挿入する」の順に実行する。各文がトリガーの検査を通るため、元枠をBだけが引き継げる。
  5. 二重の案件：同じA予約に対する進行中の案件は、部分一意インデックスで1件に制限する（AC06の同時要求を含む）。

2026-11-03の事前確認（Node v24.22.1、メモリ上のDB）：重なる予約、FROZENの保留と重なる予約、同じA予約への2件目の案件は、いずれも拒否された。隣接する予約（終了時刻＝開始時刻）は許可された。本番のスキーマとテストで改めて確認する。

5. 三者の権限とセッション

操作 店主 A B
自分のワールドの予約・案件・台帳を見る ○ 自分の予約と、自分宛ての案件だけ 自分の依頼と案件だけ
補償規定の設定 ○（それ以降の登録に適用） × ×
移動条件の登録・変更（新しい版になる） × 自分の確定予約だけ ×
依頼の入力・確認質問への回答 × × 自分の依頼だけ
振替案の承認・却下 同じterms_hashに対して 自分の予約に対する案だけ 自分の依頼に対する案だけ
支払いの開始 × × 店主とAが同じterms_hashを承認済みのときだけ
要対応の操作の再実行 既存の操作の回復だけ（新しい返金は作れない） × ×
  • 招待リンク：ワールド作成時に、役割ごとに256ビットの乱数トークンを発行し、SHA-256だけを保存する。トークンはURLのフラグメント（#以降）に入れる。フラグメントはサーバーへ送られないため、アクセスログや参照元に残らない。画面のスクリプトがトークンをPOSTでセッションに交換し、直後にhistory.replaceStateでURLから消す。Referrer-Policy: no-referrerも付ける。
  • クッキー：HttpOnly、SameSite=Strict、HTTPSではSecure。パスを/w/{ワールドID}/{役割}に限定し、1つのブラウザで三役割のタブを開いても混ざらないようにする。ただしパスの分離は表示の都合であり、認可の境界にはしない。権限の判断は、すべて次のサーバー側の検査で行う。
  • サーバー側の検査：すべてのAPIで、セッションのワールド・役割・当事者IDと、操作対象の案件・予約の所有者を照合する。画面の役割切替ボタンは招待リンクを開くだけで、認証の代わりにはしない。デモでは作成者が三役割のリンクを持つが、本来は当事者がそれぞれ自分のリンクだけを受け取る前提であることを画面とREADMEに書く。
  • CSRF：変更系のAPIは、セッションに紐付いたCSRFトークン（X-CSRF-Tokenヘッダー）とOriginの一致を必須にする。
  • 改ざん対策：ブラウザから来た金額・通貨・受取先・order ID・capture IDは使わない。サーバーは案件IDだけを受け取り、値はDBの条件スナップショットから取る（AC11）。

6. 振替の流れと状態

6.1 承認までの流れ

  1. ワールド作成：店、担当者Mika、施術2種類、Aの予約を作る。Sandboxモードでは、AがPayPal Sandboxで予約代金を支払う（intent=CAPTURE）。サーバーは売上確定の結果を照会し、金額・通貨・受取店舗・予約との紐付けを確認してから、Aの予約を「支払い確認済み」にする。模擬モードでは模擬の売上確定を使い、そのことを表示する。
  2. Aの移動条件の登録：Aが自由文で条件を書き、AIが構造化し、Aが確認して確定する（版あり）。補償額はこの時点の店の規定額で固定する（D09）。
  3. Bの依頼：Bが自由文で希望を書き、AIが構造化する。曖昧な点は質問し、Bが確認して確定する。
  4. 候補の判定（プログラム）：Bの希望枠を占めている確定予約のうち、支払い確認済みで移動条件を登録済みのA予約について、Aの条件に合う移動先を探す。担当者・施術時間・営業時間・Aの許容時間・他の予約と保留を検査する。成立しない場合は理由を表示する。
  5. 案の作成：条件スナップショットとterms_hashを作り、移動先にACTIVEの保留を置く（期限付き）。
  6. 承認：店主 → A → B の順（D08）。それぞれ同じterms_hashを承認する。Aが却下するか期限切れになれば、保留を解放し、案件は不成立になる。Bには課金しない。

6.2 実行（Bの支払い開始から完了まで）

段階 処理 次の状態
E1 実行開始 Bが条件を承認して支払いボタンを押す。BEGIN IMMEDIATEで版・期限・三者の承認・予約・保留・金額・通貨・受取先を再検査し、保留をFROZENにして条件を凍結する。同じトランザクションで、B_CHARGEの債務と、その最初の支払い試行（支払い期限つき）を作る PAYMENT_STARTED
E2 注文作成 POST /v2/checkout/orders（intent=AUTHORIZE、金額、custom_id=case:{id}:v{版}:att:{試行ID}、invoice_id=FS-{id}-B-{試行番号}）。order IDを試行に保存してから、ブラウザに返す 同上
E3 B承認 BがPayPal Sandboxの画面で承認する。ブラウザからの通知は合図としてだけ使う。与信はサーバーだけが行い、画面側のSDKで与信・売上確定を呼ばない 同上
E4 与信 試行が有効（期限内で終了していない）であることを条件付き更新で確かめ、与信の外部試行をSENDINGで記録してからPOST /v2/checkout/orders/{id}/authorizeを送る。応答で金額・通貨・custom_id（案件・版・試行）・受取先・与信の状態（CREATED）を照合する AUTHORIZED
E5 売上確定前の検査 元予約・保留・承認・凍結・与信の状態を再検査する。不成立なら取消（E-V）へ CAPTURING
E6 売上確定 POST /v2/payments/authorizations/{id}/capture（金額を明示、final_capture=true）。COMPLETEDを確認する。PENDINGなら照会を続け、予約確定へ進まない CAPTURED / PAYMENT_PENDING
E7 予約確定 1つのトランザクションで、Aの予約を移動先へ、Bの予約を元枠へ確定し、保留をCONVERTEDにし、補償の権利（予約単位で一意）と、A_COMPENSATION_REFUNDの債務・最初の試行（未送信）を作る（D05） BOOKING_COMMITTED
E8 A返金 POST /v2/payments/captures/{Aの元capture}/refund（補償額を明示）。送信前に、返金できる残額を確認する。COMPLETEDを確認する REFUND_PENDING → COMPLETED
E-V 取消 売上確定前に不成立になった場合、POST /v2/payments/authorizations/{id}/voidを送り、照会で取り消されたことを確認する VOID_PENDING → REJECTED
E-R B返金 Bの売上確定後に振替が確定的に不能になった場合、Bの売上を全額返金する（金額を明示）。Aの元予約は維持し、Aへの補償は開始しない B_REFUND_PENDING → COMPENSATED

実行権は1つだけ：E1はUPDATE swap_cases SET status='PAYMENT_STARTED' ... WHERE id=? AND status='A_ACCEPTED' AND version=?の条件付き更新で行い、更新件数が1のときだけ実行権を得る。同じ案件への確定要求が同時に2つ来ても、BEGIN IMMEDIATEで直列化されるため、2つ目は更新件数0となって拒否される（AC06、C04）。

予約確定の処理済みマーカー：E7では「案件の状態をBOOKING_COMMITTEDにする」「compensation_grantsの行を挿入する」「A_COMPENSATION_REFUNDの債務を挿入する」を、予約の更新と同じトランザクションで書く。SQLiteのコミットは原子的なので、これらは全部あるか全部ないかのどちらかになる。再起動後はこの3つの有無で、予約確定済みか未確定かを判定する（C06）。

状態名はSPEC 7の表をそのまま使い、PAYMENT_STARTED（実行開始・凍結済み）を追加する。予約、Bの与信、Bの売上確定、Aへの返金、Bへの回復返金の状態は、案件とは別にpayments、money_obligations、payment_attemptsに保存する。PayPalの状態名は加工せずに保存し、未知の状態は成功として扱わない。

6.3 Bが支払いを完了しない場合（D04、D12、DR1-01）

PayPal側の注文が「未承認」と照会できても、その直後にBが古い画面で承認する可能性がある。そこで、PayPal側の状態ではなく、FlexSlot側で試行を終了させ、終了した試行では与信を送らないことで安全を確保する。与信はサーバーの認証情報でしか実行できないため、FlexSlotが送らなければ、承認済みの注文があってもお金は動かない。

  1. 試行と版の紐付け：支払い試行は、案件・案件版・terms_hashに紐付く。注文のcustom_idに試行IDを含め、与信・売上確定の応答で照合する。
  2. 期限で終了させる条件：支払い期限（初期値15分、設定で変更可。Codex第1レビューで採用）を過ぎた時点で、BEGIN IMMEDIATEの中で次をすべて満たすときだけ、試行をEXPIRED（終端）にし、案件をEXPIRED（終端）にし、保留をRELEASEDにする。
    • その試行に、与信の外部試行が一度も記録されていない（SENDING・結果不明・成功のいずれもない）。
    • その案件に、与信・売上確定の記録がない。
  3. 送信中・結果不明なら解放しない：与信の外部試行がSENDINGまたは結果不明なら、期限を過ぎても終了させない。照会で与信の有無を確定させてから進める。
  4. 遅れて来た承認・応答の拒否：E4は「試行が有効」を条件付き更新で確かめてから与信を記録するため、期限処理と与信開始はBEGIN IMMEDIATEで直列化され、どちらか一方しか成立しない。終了した試行への承認通知、ブラウザからの再開要求、Webhookは、与信を開始せず「支払い期限切れ」を返す。
  5. 防御：照会や通知で、終了した試行に紐付く与信が見つかった場合（本来は起きない）は、ただちに取消（B_AUTH_VOID）の債務を作り、店主に要対応として表示する。
  6. 再開：期限切れの後は、同じ依頼から新しい案件（新しい版、新しい保留）を作り、店主・A・Bの承認からやり直す。古い試行や古い注文を再利用しない。
  7. 15分の意味：未承認の支払いを打ち切る検討時点であり、結果不明の処理や返金待ちの打ち切り期限ではない。通知の受信時や通常の照会は、15分を待たずに行う。

7. PayPal呼び出しの共通規則

  • Sandbox専用：接続先はhttps://api-m.sandbox.paypal.comに固定し、起動時にSandbox以外のURLを設定していれば起動を拒否する（SPEC、AGENTS）。
  • 試行を先に書く：外部呼び出しの前に、payment_attemptsの行（再送防止ID＝UUID、リクエスト本文のハッシュ、案件の版、試行ID）を状態SENDINGでコミットする。再起動後にSENDINGの行が残っていれば「送ったか不明」として扱い、送っていないとはみなさない。
  • 再送防止IDの保持期間：PayPalのRESTリクエストの資料は、IDを「最大45日」保存すると説明している（2026-11-03確認）。これは各APIで45日間の保持を保証する記述ではないため、各APIの保証、実接続で確認した範囲、未確認を区別して記録する。設計としては、数分以内の再送だけを前提にし、長期間後の再送に頼らない（STATUS U05）。
  • 結果の照合：成功と判断する前に、金額・通貨・custom_id・受取先のmerchant ID・状態を、条件スナップショットと照合する。
  • 再試行：同じ試行の通信の再送は、通信エラー、5xx、429のときだけ、間隔を2秒から倍にして最大6回まで行う。上限に達しても、外部の取引が失敗したとはみなさない。試行は結果不明のまま残し、照会での回復と店主の要対応表示に回す。

7.1 債務と試行の分離（D13、DR1-02）

  • 債務（money_obligations）：1つの案件で動かすお金の論理的な単位。種類はB_CHARGE、B_AUTH_VOID、A_COMPENSATION_REFUND、B_RECOVERY_REFUNDの4つで、(案件, 種類)は一意。金額は作成時に固定し、後から変えない。Aへの補償はさらにcompensation_grantsで予約単位に1回へ制限する。
  • 試行（payment_attempts）：債務をPayPalへ送る1回分の処理。試行ごとに新しい再送防止IDを持つ。同じ試行の通信の再送は、同じIDと同じ本文で行う。
  • 新しい試行を作れる条件：直前の試行が「確定失敗」か「受理されなかった」と判定できたときだけ。新しい試行は新しいIDを持ち、直前の試行をprevious_attempt_idで参照する。古い試行の行と外部IDは上書きせずに残す。
  • 未確定の試行は1つまで：SENDING、結果不明、PayPal側PENDINGの試行がある間は、新しい試行を作れない（部分一意インデックスで強制）。成功した試行も1つまで（同じく部分一意インデックス）。そのため、返金の合計が債務の金額を超えない。
  • 返金の前の残額確認：Aへの返金の新しい試行を作る前に、元captureを照会し、返金できる残額が債務の金額以上であることを確かめる。
  • 店主の操作：店主にできるのは「既存の債務の回復」だけ。金額や返金先を指定する任意の返金は作れない。

外部の結果を、次のように分類してから試行の状態を決める。HTTPの4xxをすべて「返金FAILED」と同じには扱わない。

観測 試行の状態 新しい試行
2xxで、リソースの状態がCOMPLETED（与信はCREATED） 成功 不要
2xxまたは照会で、リソースの状態がPENDING PayPal側PENDING。照会を続ける 作れない
照会で、リソースの状態がFAILED / CANCELLED / DECLINED 確定失敗 作れる（原因を確認してから）
この試行の最初の送信で、入力エラー（400 / 422）が返り、それ以前に結果不明の送信がない 受理されなかった 原因を直したうえで作れる
認証エラー（401 / 403） 処理されていないが、試行は終わらせない。認証を直して同じ試行を再送 作れない
「既に処理済み」を示すエラー、または結果不明の送信のあとの4xx 結果不明として照会で確定させる 作れない
通信エラー、5xx、429、タイムアウト 結果不明。同じIDで再送し、照会する 作れない

注文作成だけは例外で、注文は承認されるまでお金を動かさないため、確定失敗の判定ができない注文作成の試行は、案件の支払い期限（6.3）で終了させてよい。

7.2 貸出と書き戻しの防止（D14、DR1-03）

  • 貸出の取得：実行器も画面からの操作も、試行を処理する前にUPDATE payment_attempts SET lease_owner=?, lease_gen=lease_gen+1, lease_until=? WHERE id=? AND (lease_until IS NULL OR lease_until < ?) AND status IN (処理中に移れる状態)で貸出を取り、更新後の世代番号を手元に持つ。更新件数が0なら処理しない。
  • 結果の書き込み：外部応答の保存は... WHERE id=? AND lease_gen=? AND lease_owner=?と、許される状態遷移の条件をつけた更新だけで行う。更新件数が0なら、その応答は古いものとして業務状態に採用しない（監査ログには残す）。案件の状態の更新も、WHERE status=? AND version=?の条件付き更新で行う。
  • 時間の関係：PayPalへの1回の通信は20秒でタイムアウトさせ、貸出は60秒とする。通常は貸出が切れる前に終わる。切れた場合でも、上の世代の条件で古い書き込みを防ぐ。
  • 状態を後退させない：試行の状態には順位を付け（準備 < 送信中・結果不明 < PayPal側PENDING < 終端）、終端から非終端へ、PENDINGから送信中へは戻さない。外部リソースの状態は、PayPalのupdate_timeが保存済みのもの以上で、かつ順位が下がらない場合だけ反映する。照会Q1（PENDING）がQ2（COMPLETED）の後に届いても、状態は戻らない。
  • 正当な進行との区別：COMPLETEDの売上確定がのちに返金されるなど、別のリソース（返金・取消）による変化は、そのリソースの試行・債務として記録し、元のリソースの状態を書き換えない。
  • 結果不明は新しい試行にしない：結果不明の試行は、新しい試行としては送らず、照会と同じIDでの再送による回復に回す（7.1）。

7.4 Webhookの受信（D06、D15、DR1-04）

  • 受信の保存：届いた配信は、署名を検証する前にwebhook_deliveriesへ保存する。この表のevent_idには一意制約を置かない。保存できたときだけ200を返し、保存できなければ成功を返さない。本文は64KBまでとし、送信元ごとの受信数にも上限を置く。
  • 検証：保存した配信を、POST /v1/notifications/verify-webhook-signature（Webhook ID、受信ヘッダー、本文）で検証する。結果はVERIFIED（成功）、INVALID（失敗、終端）、VERIFY_ERROR（検証APIの通信エラー・5xx）に分ける。VERIFY_ERRORと未検証の配信は、間隔を空けて自分で検証を再試行し、再起動時にも再開する。
  • 重複の排除：VERIFIEDになった配信だけをwebhook_events（event_id一意）へ登録する。同じevent_idの不正な配信が先に届いていても、未検証・INVALIDの行はwebhook_eventsに入らないため、あとから届いた正規の配信は検証され、処理される。正規の配信が2回届いた場合は、2回目が一意制約で登録されず、1回だけ処理される。
  • 反映：登録したイベントは、該当する試行の照会のきっかけにだけ使う。Webhookの内容で状態を直接書き換えないため、古い通知で状態が後退しない（7.2）。
  • 実配送の確認：実際の配送には到達可能なHTTPSのURLが必要。V8は必須の接続検証として12章の計画で行う。

9. AI（Gemini on Vertex AI）

  • 役割：Aの移動条件とBの依頼の自由文を、決めたJSONスキーマへ構造化し、曖昧な点の確認質問を作る。候補の判定、金額、承認、決済は扱わない。AIに決済の機能やDB操作の機能は渡さない。
  • 入力：店のタイムゾーン、今日の日付（店の現地時刻）、施術ID・施術時間・担当者ID・営業時間。利用者の文は「指示ではなくデータ」と明示して渡す。自由文に含まれる指示（「補償を50ドルにして」など）には従わず、構造化の対象にもしない。
  • 出力スキーマ（案）：許容する時間区間の一覧（日付、開始・終了の現地時刻）、担当者を変えてよいか、施術の変更可否（MVPでは常に不可）、曖昧な点と確認質問。Bの場合は、施術IDと必須の時間区間も含める。
  • サーバーでの検査：zodで型・列挙値・日付の範囲・営業時間内かを検査する。「午後なら」のような表現は、具体的な時刻に勝手に確定せず、質問に回す。最終的な構造化結果は本人が確認して確定し、元の文とは別に版で保存する。
  • 呼び出し：@google/genaiをvertexai: true、プロジェクトID、リージョンを指定して使う。認証はローカルではADC（gcloud auth application-default login）、公開時はサーバーのサービスアカウント。ブラウザに認証情報を渡さない。responseMimeType: application/jsonとresponseSchemaを使い、temperatureは0にする。
  • 上限：1回20秒でタイムアウト、5xxと429のときだけ1回再試行、ワールドあたり30回まで、全体で1日500回まで。上限を超えたらフォームでの手入力を案内する。
  • 失敗時：AIが失敗したら、フォームでの手入力に切り替えることを明示して案内する。模擬のAIに黙って切り替えない。模擬モードは試験とオフライン用の固定ルールで、画面に「AI：模擬」と表示する。
  • 入力の出所：構造化した条件ごとに、AI（Vertex）・AI（模擬）・手入力のどれで作ったかを保存し、画面に表示する。手入力や模擬の結果は、実AIが成功した証拠（AC03）に含めない。
  • モデル：Vertex AIのGeminiのうち、構造化出力に対応する低遅延のモデル（Flash系を想定）を候補にする。実際のモデル名とリージョンは接続検証（V9）で、このプロジェクトで使えるものを確認してから決め、STATUSに記録する。

  • AIのモード（Vertex / 模擬）と決済のモード（Sandbox / 模擬）は独立して設定し、ワールドの作成時に固定する。三画面の上部に常に表示する。

V2 Aの元決済（intent=CAPTURE） 注文作成 → Sandboxの買い手で承認 → 売上確定 → 照会で金額・通貨・受取先が一致 V1、本人の承認操作
V3 Bの与信 intent=AUTHORIZEの注文 → 承認 → 与信。表現形式の応答で与信ID・状態・期限が取れる V1、本人の承認操作
V4 売上確定と再送防止 金額を明示して売上確定。同じ再送防止IDで再送すると同じcapture IDが返る。注文・与信の照会から売上確定を特定できるかも確認する V3
V5 与信の取消 別の与信を取り消し、照会でVOIDEDになる V3
V6 Aへの部分返金 元captureへ10.00を返金し、同じIDで再送すると同じ返金IDが返る。返金と元captureの照会で状態・残額が分かる。残額を超える返金はエラーで拒否される V2

V9 Vertex AIの構造化出力 選んだモデル・リージョンで、A・B・曖昧な文の3例がスキーマどおりに返る。遅延と使用量を記録。タイムアウト時の扱いも確認 本人：プロジェクト、課金、Vertex AI API、gcloud、ADC

12.1 V8の進め方（D16、DR1-05）

V8は、公開デモを用意するかどうかに関係なく必須とする（AC07）。

  1. 受信経路の候補：(a) 公開デモを承認された場合はそのVMのHTTPSのURL。(b) 公開デモを用意しない場合も、検証の時間帯だけ/webhooks/paypalへの経路に限って外部から届く限定的なHTTPS受信経路を用意する（トンネルの場合は経路をこのパスだけに絞る）。どちらも外部公開にあたるため、受信先・公開する範囲・時間帯・停止方法を示して本人確認を受けてから行う。
  2. 時期：Sandboxで一件が最後まで通った後（11月7日の目標）。
  3. 合格の証拠：PayPalの開発者画面での配送記録と、webhook_deliveries・webhook_eventsの行（VERIFIED、処理済み）が、同じ取引で一致すること。改ざんした配信がINVALIDになり、正規の配信の処理を妨げないこと。
  4. 合格にしないもの：RESTの照会だけでの成功、Webhook Simulatorだけのイベント、模擬の署名検証。
  5. 未承認のとき：受信経路の承認が得られない間は、V8とAC07を未確認として残し、完成とは報告しない。

模擬モードの障害注入テスト（通信切断、5xx、PENDING、二重のWebhookなど）は、Sandboxで同じ失敗を再現した証拠とは区別して記録する（SPEC 10）。

15. 第1レビュー指摘への対応（design-v0.2）

指摘 対応した箇所 要点
DR1-01 / P1 6.2のE1・E2・E4、6.3、8章の「B未承認のまま離脱」、D12、AC05 支払い試行を案件版に紐付け、期限で試行を終了させる。与信開始と期限処理はBEGIN IMMEDIATEで直列化し、終了した試行では与信を送らない。与信が送信中・結果不明なら解放しない。再開は新しい案件と再承認。PayPal側の未承認状態を取消とは扱わない

DR1-03 / P1 7.2、2章の単一プロセスの補足、D14、AC08 貸出の所有者と世代番号、結果の書き込みは世代・状態・版を条件にした更新だけ。状態の順位とupdate_timeで後退を防ぐ。結果不明は新しい試行にしない
DR1-04 / P2 3章のwebhook_deliveries・webhook_events、7.4、D15、AC07 受信の保存と、検証済みイベントの重複排除を分離。検証APIの一時失敗は自分で再試行し、再起動時にも再開
